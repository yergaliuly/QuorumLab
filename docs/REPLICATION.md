# M3: как записи становятся общим журналом

В M2 узлы выбирали лидера. В M3 лидер передаёт записи, исправляет расхождения и определяет, что уже можно применить. Код выборов расширен до [RaftNode](../quorum-core/src/main/java/io/github/yergaliuly/quorumlab/core/RaftNode.java); отдельного второго алгоритма нет.

## Что означают индексы

| Поле | Смысл | Пример |
|---|---|---|
| index | Номер записи в журнале | Запись 4 следует за записью 3 |
| term записи | Раунд лидера, который создал запись | index=4 может иметь term=7 |
| nextIndex[B] | С какой записи лидер пробует продолжить передачу B | 4 означает prevLogIndex=3 |
| matchIndex[B] | До какого индекса B подтвердил устойчивое совпадение | 3 — данные до 3 уже сохранены |
| commitIndex | Подтверждённый префикс, который нельзя заменить | После commit=4 записи 1…4 защищены |
| lastApplied | До какого индекса consumer завершил применение | Может отставать от commit |

В памяти лидера commit может опережать сохранённый commit во время записи. Поэтому эффекты apply и объявления leaderCommit используют **durable commit**, а не только текущее число в памяти.

## Одна команда от входа до применения

Пусть A — лидер term=7, а NO_OP при избрании уже находится на index=1 и подтверждён. Теперь внутренний стенд передаёт A `Propose([42])`. Это один opaque байт для проверки, не готовая PUT-команда.

1. A проверяет роль и готовность storage, создаёт `LogEntry(2,7,COMMAND,[42])`. Возвращает ProposalQueued(2,7) и PersistBatch. Queued ещё не означает успех для клиента.
2. WalStorage сохраняет batch; FileWal завершает WAL/checkpoint/force-протокол. В очередь приходит PersistCompleted с тем же ID. Теперь запись можно отправлять.
3. A посылает B `AppendEntries(term=7, prev=1/7, entries=[2/7], leaderCommit=1)`.
4. B проверяет term и свою запись 1/7. Он добавляет запись 2, сохраняет её и только после completion отвечает `success=true, matchIndex=2`.
5. A учитывает свою durable запись и ответ B: это 2 из 3. Запись 2 создана в текущем term=7, значит можно продвинуть commit до 2. Сначала A сохраняет новое commit metadata.
6. После completion A выдаёт `ApplyCommittedEntries([entry 2])` и сообщает followers leaderCommit=2. Consumer выполняет работу, возвращает ApplyCompleted; только теперь lastApplied=2.

Если процесс упал между записью на диск и completion, результат записи для старого core неизвестен. При restart FileWal читает подтверждённый checkpoint; новый core получает фактический durable журнал. Старые completion IDs не принимаются.

## Как исправляется конфликт

```text
              index: 1  2  3  4
Лидер, terms:        1  2  5  5
Follower, terms:     1  2  3  3
commit follower:        2
```

Запрос с prev=4/5 не совпадёт. Лидер уменьшает nextIndex и повторяет. Когда prev=2/2 совпадает, follower видит конфликт на index=3: удаляет только suffix с 3 и добавляет записи 3/5, 4/5. Truncate и append входят в один durable batch.

Короткий совпавший запрос сам по себе хвост не обрезает. Даже пустой heartbeat проверяет prev. Если он проверил только index=2, он не может сделать commit=4 по неподтверждённым локальным записям 3 и 4.

## Почему большинства копий бывает недостаточно

A хранит запись index=2, term=2. B её ещё не имеет. C хранит на том же индексе другую запись term=3. A избирается в новом term с помощью B и копирует старую term-2 запись на B.

Теперь старая запись есть на A+B, но она всё ещё **не committed**: term записи не равен текущему term лидера. Если A отключится до репликации новой NO_OP, C может выиграть следующие выборы благодаря более свежему журналу и заменить неподтверждённый suffix B.

Если A успеет подтвердить свою новую NO_OP текущего term, вместе с ней подтверждается весь предшествующий префикс. Именно поэтому новый лидер добавляет NO_OP, даже если клиент пока ничего не пишет. Это правило из [Raft §5.4.2](https://raft.github.io/raft.pdf), проверенное нашим Figure 8 regression для трёх voters.

## Повторы, задержки и простой контроль нагрузки

На каждого follower лидер хранит один запрос в полёте. Пока нет ответа, heartbeat повторяет тот же запрос с тем же OperationId. Если на каждом тике выдавать новый ID, при медленной сети все ответы могут оказаться устаревшими и прогресс остановится.

После ответа проверяются отправитель, term, requestId и точный matchIndex. Старый отказ не уменьшит nextIndex после более нового успеха. Более высокий term вызывает step-down даже в запоздавшем ответе: это информация о новом раунде протокола.

Здесь выбран stop-and-wait. Pipelining может ускорить передачу, но требует более сложной обработки ответов и окна запросов. Для этого этапа важнее проверить корректность. Размер одного append ограничен числом записей и байтами payload.

## Какие технологии реально участвовали

- **Java 21 records/sealed interfaces** описывают входы и эффекты. Например, switch по RaftEvent требует учесть добавленные ApplyCompleted/ApplyFailed. Массив команды копируется при входе/чтении, чтобы внешний код не изменил уже принятую запись.
- **Event/effect boundary** отделяет решение от исполнения. RaftNode решает «сохранить batch», WalStorage исполняет его; очередь возвращает completion. Так один алгоритм работает и в виртуальном стенде, и с настоящим диском.
- **Существующий WAL/CRC32C/checkpoint** сохраняет журнал. Новый M3-адаптер связывает truncate/append/commit в один пакет; дисковый формат не менялся.
- **Детерминированный scheduler и seeded Random** дают повторяемые задержки и выборы. RaftSimulation моделирует сеть и диск, отдельно проверяя durable prefix и применённые записи. Реальных сокетов здесь нет.
- **JUnit 5, Gradle Wrapper и ArchUnit** запускают regression/safety/integration tests и защищают pure core. **WSL/ext4** нужен для реальных filesystem checks: данные тестов находятся в build/tmp/test-files снимка, не в системном tmpfs.

Новых внешних библиотек M3 не добавил. Netty, protobuf, HTTP, готовая KV state machine и snapshot пока не использованы.

## Что проверено и какая ошибка возникла

Контрактные тесты сначала не компилировались без новых типов; после реализации прошли. Симулятор сначала не компилировался со старым heartbeat API; затем обновлён под AppendEntries. При добавлении реальных WAL-тестов компилятор выявил пропущенное `throws IOException` у помощника seed: исправлена сигнатура, реальные Linux-тесты прошли.

Отдельный отрицательный эксперимент временно отключал current-term guard. Unit и Figure 8 tests оба обнаружили ложный commit: ожидали 0, получили 2. Правильный guard восстановлен до финальных сборок. Это намеренная проверка тестов, не найденный дефект рабочей реализации.

Финальные результаты, команды, ограничения и точный Linux snapshot — в [ACCEPTANCE](ACCEPTANCE.md). Следующий этап M4 даст байтам смысл PUT/GET/DELETE/CAS и добавит клиентскую дедупликацию. До него ProposalQueued нельзя выдавать за успешный ответ KV-клиенту.
