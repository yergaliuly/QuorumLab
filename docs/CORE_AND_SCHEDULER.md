# M0: как работают контракты и планировщик

В этом срезе появились первые Java-исходники. Работают проверка входных DTO и очередь виртуальных событий. `RaftCore`, Storage/Transport и RNG пока задают интерфейсы; алгоритм, диск, сеть и генератор случайных задержек ещё не реализованы.

## Событие → ядро → эффекты

**Событие** сообщает о случившемся: пришло сообщение, сработал таймер, закончилось сохранение. **Эффект** описывает работу для внешнего компонента: отправить сообщение, сохранить состояние, поставить таймер.

```java
List<Effect> step(RaftEvent event);
```

`interface` — договор о вызове: другой модуль знает, какие данные передать и что получить, без знания внутренней реализации. Будущее ядро будет хранить состояние между вызовами `step`; одинаковые начальное состояние, события и явно переданные случайные выборки должны давать одинаковые переходы и эффекты. Сейчас написан только этот договор.

`List<Effect>` позволяет вернуть несколько независимых действий или `List.of()` для отсутствия действий. Порядок элементов не доказывает завершение асинхронного I/O. Реализация обязана возвращать неизменяемый список.

**Пример будущего голосования, не работающая election-функция текущего кода:**

1. Узел B получает `RpcReceived(A, RequestVote(term=3, lastLogIndex=7, lastLogTerm=2))`.
2. Если будущий алгоритм разрешает голос, он возвращает `PersistHardState(id=(1,5), state=(3, A, commitIndex))` и запоминает ожидаемый ID.
3. Адаптер сохраняет метаданные и ставит `PersistCompleted((1,5))` в очередь B.
4. Только после обработки этого события и повторной проверки текущего term ядро может вернуть `SendRpc(A, VoteResponse(3, true))`.

Если сначала отправить голос, а запись потерять при падении, узел может забыть свой голос и проголосовать снова. Поэтому нужен отдельный completion. При `PersistFailed` устойчивый результат неизвестен: положительный ответ запрещён. Эти правила описаны в [ADR-002](adr/0002-core-events-and-virtual-time.md); их исполнение и safety-тесты предстоят в M1/M2.

`HardState` — устойчивые метаданные: `currentTerm` (раунд Raft), `votedFor` (кому отдан голос) и `commitIndex` (граница подтверждённого журнала). Например, term=2 и commitIndex=100 допустимы: за один раунд лидер может подтвердить много записей. `HardState.initial()` задаёт term=0, отсутствие голоса и commitIndex=0. Объект в памяти сам ничего не сохраняет.

## Конструкции Java, которые мы использовали

| Конструкция | Что делает | Пример в проекте |
|---|---|---|
| `record` | Создаёт класс данных с final-полями, accessor-методами, equals/hashCode | Два `NodeId("a")` равны по значению; два одинаковых trace можно сравнить |
| Compact constructor | Проверяет аргументы record до создания объекта | `new OperationId(1, 0)` бросает исключение: sequence должен быть положительным |
| `sealed interface` | Ограничивает список допустимых реализаций | Все текущие виды RaftEvent явно перечислены вложенными records |
| `Optional<NodeId>` | Явно представляет наличие/отсутствие значения | Нет голоса — `Optional.empty()`, а не особое имя узла или null |
| Generic `<E>` | Позволяет типобезопасно использовать один алгоритм с разными payload | `DeterministicScheduler<RaftEvent>` принимает только RaftEvent |
| `PriorityQueue` + `Comparator` | Выбирает минимальный элемент по заданным полям | Сначала время, затем порядок добавления |

Record не делает вложенный изменяемый объект автоматически неизменяемым. У наших DTO компоненты — числа, boolean, enum, String, Optional и другие неизменяемые records. Массивов и изменяемых коллекций в них сейчас нет. Для будущих byte payload потребуется отдельное решение о копировании.

`OperationId(incarnation, sequence)` отличает операции и запуски одного узла. Например, completion `(1,5)` не равен `(2,5)` после restart. Создание ID ещё не обеспечивает фильтрацию: будущий driver/core должны проверять его, а runtime — назначать новую incarnation.

## Действительно работающий scheduler

Планировщик хранит очередь и два числа: текущее время и следующий порядковый номер. Время измеряется целым `long` в наносекундах от условного нуля; календарной даты нет. Одна миллисекунда — 1 000 000 наносекунд.

```java
var scheduler = new DeterministicScheduler<String>();
var a = new NodeId("a");
var b = new NodeId("b");

scheduler.scheduleAt(20_000_000, a, "таймер A");
scheduler.scheduleAt(10_000_000, b, "сохранение B");
scheduler.scheduleAt(10_000_000, a, "сообщение A");

var first = scheduler.pollNext().orElseThrow();
// first.payload() == "сохранение B"; scheduler.nowNanos() == 10_000_000
```

Порядок извлечения:

| Виртуальное время | Порядковый номер | Узел | Payload |
|---|---|---|---|
| 10 мс | 1 | B | сохранение B |
| 10 мс | 2 | A | сообщение A |
| 20 мс | 0 | A | таймер A |

Приоритет времени важнее номера вставки. При одинаковом времени раньше добавленное событие идёт первым, даже если оно адресовано другому узлу. Добавленное сейчас событие с нулевой задержкой встаёт после уже ожидающих событий этого же времени.

`scheduleAt` принимает абсолютное виртуальное время. `scheduleAfter(7, ...)` при `nowNanos() == 10` добавит событие на 17 нс. Добавление не двигает часы. `pollNext` извлекает один элемент, двигает часы и возвращает данные; обработку узлом он не вызывает. Пустая очередь возвращает `Optional.empty()` и оставляет время прежним.

Нет `Thread.sleep` и ожидания 20 реальных миллисекунд. Это важно для будущих тысяч сценариев с задержками. `Math.addExact` запрещает переполнение: слишком большая задержка вызывает исключение вместо превращения будущего времени в отрицательное.

Scheduler работает в одном потоке. Он не содержит отмены, диспетчеризации, падений узлов, simulated disk/network или автоматического цикла обработки. Произвольный generic payload должен быть неизменяемым. Более полный simulator появится постепенно.

## Порты и зависимости модулей

Порт — интерфейс на границе компонентов. `Storage.persist` принимает описание сохранения; `Transport.send` — отправки. Реальный и simulated адаптер смогут реализовать один интерфейс разными способами. Возврат из метода не означает durable persistence или доставку сообщения.

`MonotonicClock.nowNanos()` позволяет читать время, не зная его источник. Scheduler уже реализует этот порт. `RandomSource.nextLong(origin, bound)` задаёт контракт выбора числа в полуинтервале `[origin, bound)` для будущих election timeout; реализации seeded RNG пока нет.

В Gradle появилась зависимость `quorum-simulator → quorum-core`. Использован `api`, потому что `NodeId` и `MonotonicClock` видны в публичном API scheduler. Поэтому будущий модуль, использующий simulator, должен видеть эти типы и при компиляции. У core производственных зависимостей по-прежнему нет; JUnit подключён только к тестам.

## Проверки и следующий шаг

JUnit запускает 44 случая: 36 в CoreContractsTest (включая параметризованные недопустимые/null-входы) и 8 в DeterministicSchedulerTest. Проверяются начальные метаданные, значение идентичности операций, ограничения DTO, хронология, FIFO, вставка после извлечения, повтор trace, пустая очередь, недопустимое время и overflow без повреждения состояния.

Сначала тесты обнаружили отсутствующую валидацию (32 падения) и отсутствующую реализацию scheduler (8 падений). Это намеренный RED тестовой разработки, не обнаруженный дефект готовой системы. После реализации все 44 случая прошли на Windows и WSL Linux. Подробные свидетельства — в [ACCEPTANCE](ACCEPTANCE.md).

Эти тесты не проверяют выборы, persist-before-response, запись на диск или реальный restart. Новый GitHub CI запустится после пользовательского push. Следующий небольшой срез M0 — ADR-001 и автоматический контроль границ core; затем M1 Storage по дорожной карте.
