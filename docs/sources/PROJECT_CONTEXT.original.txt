# QuorumLab — техническое задание и архитектура

Версия ТЗ 1.0

Java Backend / Distributed Systems

Research-grade Portfolio

QuorumLab — собственная распределённая Key-Value база данных на Java с реализацией алгоритма консенсуса Raft, устойчивым хранением данных и системой детерминированного тестирования отказов.

Мы будем разрабатывать не копию PostgreSQL, а самостоятельный инфраструктурный продукт, который демонстрирует знания алгоритмов, конкурентного программирования, сетей, хранения данных и отказоустойчивости.

Главная инженерная цель:

> Создать кластер, в котором несколько серверов согласованно обрабатывают запросы, а затем построить систему, способную воспроизводимо находить ошибки в его работе.

Именно сочетание собственной базы данных + собственной реализации Raft + Chaos Engineering Lab будет главным отличием проекта.

## 1. Какие результаты считаем успехом

Собственное хранилище

Данные сохраняются на диск. Выключение и повторный запуск процесса не уничтожают успешно подтверждённые записи.

Распределённый кластер

Три узла согласуют операции через Raft. Кластер может продолжать работу при отказе одного узла, если оставшиеся два способны обмениваться сообщениями.

Корректность важнее скорости

Подтверждённые операции не теряются, узлы не применяют разные команды на одной позиции журнала, а клиентские операции соответствуют заявленной модели согласованности.

Собственная испытательная лаборатория

Можно выключать лидера, разделять сеть, задерживать пакеты, имитировать сбои диска и повторять конкретный неудачный эксперимент по seed и журналу событий.

Опорой будут оригинальная спецификация [Raft](https://raft.github.io/?utm_source=chatgpt.com) и практические материалы [MIT Distributed Systems](https://pdos.csail.mit.edu/6.5840/labs/lab-raft1.html?utm_source=chatgpt.com). Аналогичное сочетание моделирования и испытания отказов используется в FoundationDB.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://raft.github.io\&sz=32)

raft.github.io+2



Принципиальное архитектурное решение: все ключевые алгоритмы пишем самостоятельно на Java. Готовые библиотеки используем для HTTP, сериализации, метрик и тестов, но не для реализации самого Raft или хранения состояния базы данных.

### Что означает каждый компонент

| Компонент        | Ответственность                                     | Почему нужен                             |
| ---------------- | --------------------------------------------------- | ---------------------------------------- |
| Raft Core        | Выборы лидера, термы, журнал, репликация            | Согласованность между узлами             |
| KV State Machine | PUT, GET, DELETE, CAS                               | Собственно операции с данными            |
| WAL Storage      | Запись на диск и восстановление                     | Защита от потери подтверждённых операций |
| Node Runtime     | Соединяет алгоритм с сетью и диском                 | Изоляция бизнес-логики от инфраструктуры |
| Chaos Simulator  | Имитирует сеть, время, отказы                       | Поиск редких ошибок                      |
| History Checker  | Проверяет корректность последовательностей операций | Независимая проверка гарантий            |
| Dashboard        | Визуализирует состояние кластера                    | Демонстрация и отладка                   |

Самое важное решение — Raft Core должен быть независим от сети, системных часов, диска и Spring Boot.

Например, алгоритм получает событие `ElectionTimeout` и выдаёт эффекты: сохранить новое состояние, отправить RequestVote другим узлам, установить следующий таймер.

В реальном режиме эти эффекты исполняет Java runtime. В симуляторе — виртуальный scheduler. Алгоритм остаётся тем же.

## 4. Как будет работать запись

Допустим, пользователь записывает `balance = 500`.

1. Клиент отправляет PUT

   Запрос приходит к лидеру кластера.
2. Лидер добавляет команду в WAL

   Запись должна стать долговечной на диске до того, как лидер сможет учитывать её как надёжно сохранённую.
3. Followers получают AppendEntries

   Они проверяют журнал и сохраняют новые записи перед успешным подтверждением.
4. Получено большинство подтверждений

   В трёхузловом кластере требуется 2 из 3, включая лидера, с соблюдением правил Raft для текущего term.
5. Команда становится committed

   Лидер применяет её к KV State Machine.
6. Клиент получает успешный ответ

   Только теперь мы возвращаем подтверждение.

Почему это существенно?

Если лидер отправит `200 OK` до надёжной репликации и сразу упадёт, новый лидер может не иметь этой записи. Клиент будет считать операцию успешной, хотя данные исчезли.

Поэтому порядок persist, replicate, commit и apply — это вопрос корректности, а не просто оптимизации. Документация etcd Raft особо выделяет требования к сохранению HardState и log entries перед отправкой зависящих от них сообщений.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub+1



Для чтения мы сначала используем простую, но корректную схему: `GET` проходит через Raft-журнал. Позднее реализуем ReadIndex, чтобы не записывать каждое чтение в лог. Главное — не разрешать изолированному старому лидеру отвечать устаревшими значениями.

## 5. Технологический стек

| Область              | Выбор                             |
| -------------------- | --------------------------------- |
| Основной язык        | Java 21                           |
| Сборка               | Gradle Kotlin DSL                 |
| Консенсус            | Собственная реализация Raft       |
| Network transport    | gRPC + Protocol Buffers           |
| Storage              | Собственный WAL + snapshots       |
| HTTP API             | Spring Boot как отдельный adapter |
| Тестирование         | JUnit 5, AssertJ, jqwik           |
| Fault injection      | Собственный simulator + Toxiproxy |
| Интеграционные тесты | Testcontainers, Docker            |
| Наблюдаемость        | Micrometer, Prometheus, Grafana   |
| Frontend             | React + TypeScript                |
| CI/CD                | GitHub Actions                    |

Почему я не добавляю PostgreSQL, Redis и Kafka?

Потому что в этом проекте мы сами разрабатываем механизм хранения, согласования и репликации. Дополнительные инфраструктурные сервисы создадут сложность, не приближая нас к основной цели.

При этом gRPC использовать нормально: ты демонстрируешь собственную реализацию алгоритмов, а не умение повторно реализовать TCP.

## 7. Как будем тестировать

Это важнейшая часть всего проекта.

Примеры обязательных сценариев:

| Сценарий                               | Что мы должны доказать                               |
| -------------------------------------- | ---------------------------------------------------- |
| Лидер выключился после успешного PUT   | Данные не потерялись                                 |
| Старый лидер оказался изолированным    | Он не подтверждает новые линейризуемые операции      |
| Повтор запроса после timeout           | Операция не применяется дважды                       |
| Разные узлы имеют конфликтующие записи | Неподтверждённый суффикс безопасно исправляется      |
| Snapshot создаётся во время сбоя       | Восстановление не повреждает согласованное состояние |
| Случайный тест обнаружил нарушение     | Ошибку можно воспроизвести по сохранённой трассе     |

Для сетевых интеграционных тестов пригодится Toxiproxy, который поддерживает имитацию плохих сетевых условий.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://testcontainers.com\&sz=32)

Testcontainers



Особое внимание — linearizability. Если завершилась запись `x=10`, а уже после неё началось чтение, оно не должно возвращать более старое значение при отсутствии последующих изменений. Конкурентные операции проверяются с учётом их реальных интервалов выполнения. Для этого подходят независимые history checkers, такие как Jepsen Knossos.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub+1



Уровни проверки будут различаться: быстрые unit-тесты на каждый commit, property-based проверки на PR, полноценные многопроцессные тесты перед релизом и долгие симуляции отдельно. В документе заложена целевая nightly-проверка 10 000 seeds; это план, а не уже достигнутый результат.

## 8. С чего конкретно начнём

Первый технический шаг — M0: Foundation, а не немедленное написание Raft.

В этом этапе мы создаём репозиторий, Gradle-модули и фиксируем четыре контракта: `RaftEvent`, `Effect`, `Storage` и `Transport`. Затем пишем самый простой виртуальный event scheduler и первый тест перехода состояния узла.

Это поможет избежать ситуации, когда Raft намертво связан с потоками, сокетами и `System.currentTimeMillis()`, а для симуляции его приходится переписывать.

Первый PR должен запускаться командой:

```
./gradlew clean test
```

И проходить в GitHub Actions. Он ещё не будет содержать рабочую распределённую базу данных — только проверяемый фундамент, на котором мы постепенно её построим.

## 9. Какой результат будет особенно ценным для портфолио

Я вижу главный демонстрационный сценарий так: запускаются три узла, выполняется запись, затем мы отключаем лидера. Новый лидер выбирается, подтверждённые данные сохраняются. Мы разрываем сеть, показываем отказ от небезопасных операций, восстанавливаем связь и запускаем проверку истории.

После этого открываем тестовый отчёт с журналом событий и показываем, какие именно свойства системы проверены и какие сценарии пока не покрыты.

Такой проект будет интересен не только работодателям в Java Backend, но и командам, занимающимся databases, storage infrastructure, distributed systems и reliability engineering.

Следующий практический шаг: создать репозиторий `quorumlab`, добавить подготовленное ТЗ и реализовать M0 — структуру проекта, интерфейсы ядра и первый детерминированный тест. Это даст нам прочную основу для дальнейшей разработки без преждевременного усложнения системы.
