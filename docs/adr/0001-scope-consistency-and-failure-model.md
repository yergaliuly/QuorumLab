# ADR-001: границы v1, согласованность и модель отказов

Дата: 2026-11-09. Статус: принято для v1.

Основание: [ТЗ v1.0, разделы 1–3, 5–8](../TECHNICAL_SPECIFICATION.md), ранее выбранное направление и прямой запрос пользователя завершить фундамент M0. Этот ADR фиксирует существующий объём, а не добавляет продуктовые возможности. Ниже описаны **целевые гарантии**; фактически пройденные проверки перечислены отдельно в [ACCEPTANCE](../ACCEPTANCE.md).

## Контекст и выбор

QuorumLab — учебный Java KV-store с собственными Raft/WAL и детерминированной лабораторией отказов. Главный результат — проверяемая корректность. Готовый Raft или готовая база как runtime-основа скрыли бы задачи проекта. Поэтому сохраняем собственное ядро и журнал; готовые реализации допустимы как источники для изучения.

## Топология и объём

- Одна Raft-группа, ровно три постоянных voting nodes; quorum = 2. У каждого собственные nodeId, JVM-процесс и каталог данных; clusterId общий и проверяется при взаимодействии/recovery.
- Выборы лидера и репликация — Raft; операции — PUT, GET, DELETE и CAS по revision. В памяти — детерминированная KV state machine; на диске — собственный WAL, метаданные и snapshots.
- Membership неизменяем в v1. Динамический состав потребовал бы отдельного протокола reconfiguration и новых safety-проверок; он отложен.
- SQL, вторичные индексы, многоключевые транзакции, sharding, LSM-tree, multi-tenancy, многорегиональное развёртывание и production auth/TLS вне объёма. Dashboard следует за рабочим и проверенным backend.
- Служба запускается на localhost или в изолированной сети. Публичное неаутентифицированное развёртывание не является поддерживаемым сценарием.

## Согласованность и ответы клиенту

1. Цель — линейризуемость завершённых KV-операций: результат согласуется с последовательным выполнением, сохраняющим порядок неперекрывающихся запросов. Например, после успешного PUT(x, 1) следующий GET(x) при отсутствии других записей не должен вернуть старое значение.
2. Начальный GET проходит через Raft-log и упорядоченное применение. Это проще проверить, чем отдельный протокол чтения, хотя дороже по I/O. Локальное чтение бывшего лидера недостаточно. ReadIndex — возможная последующая оптимизация с отдельным решением; lease reads в v1 исключены.
3. Успех мутации — после durable записи на quorum и локального применения committed команды лидером. Только подтверждённые записи применяются по порядку. Продвижение commit подсчётом большинства использует запись текущего term; старые записи подтверждаются косвенно.
4. Без доступного большинства новые линейризуемые операции не получают ложный успех. Диагностический `/v1/status` не является линейризуемым KV-чтением.
5. Timeout не означает, что запись не состоялась. При неизвестном исходе клиент повторяет тот же запрос, сохраняя идентификатор и байты команды. Для мутаций задан `(clientId, requestSeq, payloadHash)`, один in-flight запрос на клиента и сохранение результата для dedup/replay/snapshot. Это не гарантия exactly-once доставки по сети.
6. Базовые API-ограничения сохраняются из ТЗ: ключ UTF-8 до 256 байт, значение до 64 KiB, лимит клиентских сессий задаётся конфигурацией; автоматического удаления сессий в v1 нет. Revision связана с log index изменившей ключ мутации, tombstone сохраняет revision. Спорные детали ошибок и no-op операций перечислены ниже, а не выбраны молча.

## Модель отказов

- Сеть асинхронная: drop/delay/duplicate/reorder, направленные partitions и потеря ответа допустимы. Для safety нет предположения о фиксированной максимальной задержке.
- Узел может остановиться/упасть и затем перезапуститься, потеряв volatile state. Byzantine-узлы и намеренная подделка сообщений не рассматриваются.
- Для liveness требуется достаточно долгий период работы и связи большинства, подходящие тайм-ауты и доступное хранилище. Фиксированное время election и прогресс при произвольных задержках не обещаются.
- Модель диска включает задержки/ошибки записи, ENOSPC и partial tail. В симуляции crash до подтверждённого force может потерять буфер, после force подтверждённое содержимое сохраняется. Реальное recovery обязано различать незавершённый хвост и повреждение устойчивых данных; точные правила формата будут приняты перед M1.
- Term/vote сохраняются до зависимого ответа; log/commit/apply соблюдают persist-before-response и порядок из [ADR-002](0002-core-events-and-virtual-time.md). Ошибка persistence не разрешает положительный ответ; узел прекращает участие до recovery. Наличие DTO не доказывает выполнение этого правила.
- Поддерживаемая платформа будущих disk guarantees — проверенная Linux-среда. Для разработки выбран WSL2 Ubuntu с каталогами на ext4 внутри Linux. Windows checkout и `/mnt/c` остаются удобны для редактирования/обычных Java-тестов, но не используются как свидетельство Linux durability.
- Проверка процесса restart не равна проверке физического power loss. Ни ext4, ни успешный build сами по себе не доказывают устойчивость WAL. Неисправное оборудование, нарушающее контракт force/fsync, и непроверенные filesystem вне заявленных гарантий. Для power loss потребуется отдельная модель и system/hardware evidence.

## Архитектурные последствия

Core не выполняет I/O, не создаёт потоки, не читает системное время и не выбирает случайность из глобальных источников. Внешний мир представлен событиями/эффектами и явно переданными портами; production и simulator используют один алгоритм. Seed и полный trace имеют смысл в рамках одного build/config, а не как обещание одинакового поведения разных версий.

Граница закрепляется двумя проверками: Gradle запрещает любые production compile/runtime dependencies core; ArchUnit проверяет все production class-файлы на запрещённые типы/API. Тестовые зависимости разрешены. Эти проверки ловят обычные статические нарушения, но не являются sandbox против reflection/native обходов и не доказывают детерминизм произвольной программы.
