# ADR-002: события ядра и виртуальное время

Дата: 2026-11-09. Статус: принято для начального среза M0.

Основание: модель event → effects задана [ТЗ §4](../TECHNICAL_SPECIFICATION.md); пользователь поручил реализовать контракты, простой scheduler и тесты в одной ветке. Конкретные имена DTO, единица времени и структура ID ниже — решения реализации, а не цитаты исходного ТЗ. ADR-001 о полном scope/failure model остаётся отдельным шагом.

## Контекст

Один алгоритм должен работать с настоящими адаптерами и симулятором. Вызов сети или диска из алгоритма усложнил бы воспроизводимые проверки. Возврат двух эффектов подряд не означает, что первый уже устойчиво выполнен: список `persist, send` сам по себе не обеспечивает persist-before-response.

## Решение

1. `RaftCore.step(RaftEvent)` — граница stateful детерминированного ядра. Один driver вызывает её последовательно, без повторного входа из callback. Реализации алгоритма в этом срезе нет. Контракт требует неизменяемый список эффектов без `null`; Java-интерфейс сам это не проверяет.
2. Первые sealed-события: `TimerFired`, `RpcReceived`, `PersistCompleted`, `PersistFailed`. Эффекты: `PersistHardState`, `SendRpc`, `ScheduleTimer`. RPC пока только `RequestVote` и `VoteResponse`. Отправитель в `RpcReceived.from` является candidateId для RequestVote; будущий transport обязан сохранять эту связь и проверять membership/cluster envelope.
3. DTO — records с неизменяемыми компонентами. Конструкторы отвергают null, отрицательные счётчики и локально невозможные сочетания. Проверка переходов между состояниями, например запрет отката term, относится к будущему алгоритму. `HardState` включает term, optional vote и commitIndex; index не ограничивается номером term.
4. `OperationId(incarnation, sequence)` положителен и уникален в пределах узла. Runtime выдаёт новую incarnation при restart, ядро не переиспользует sequence в её пределах. Это идентификатор корреляции, не client dedup и не Raft term. Аллокатора и restart runtime пока нет.
5. Ядро хранит ожидаемый ID сохранения. Зависимый `SendRpc` возвращается только отдельным вызовом `step` после соответствующего `PersistCompleted` и повторной проверки актуального term/состояния. Чужой, повторный или устаревший completion не разрешает старый ответ. При смене term нельзя просто забыть незавершённую запись: она всё ещё может попасть на диск. Начальный driver должен сериализовать сохранения узла (не более одного in-flight), чтобы старое состояние не перезаписало новое.
6. `PersistFailed` означает неизвестный устойчивый исход; он не является успешным сохранением и не разрешает зависимые ответы. Будущий runtime останавливает участие такого узла в протоколе до recovery; слепой retry поверх неизвестного состояния не задан. `commitIndex` можно сохранять только после устойчивости соответствующих log entries. `ApplyCommittedEntries` появится в M3: применение только committed entries по порядку; durable ack не равен commit/apply.
7. Каждый запуск таймера имеет новый OperationId. После перевзвода ядро должно игнорировать старый ID. Scheduler не удаляет такие события и не решает за ядро, актуальны ли они. При restart driver проверяет incarnation до доставки событий нового/старого запуска.
8. `Storage` и `Transport` — порты driver, без реализаций. Возврат `persist` не означает durable success: адаптер ставит completion/failure с тем же ID в очередь узла. `send` не обещает доставку. Clock/RNG передаются явно, без глобальных часов или случайности. Seeded RNG ещё не реализован.
9. Scheduler однопоточный, начинает с 0 и сортирует по `(timeNanos, insertionOrder)`. `scheduleAt` добавляет событие, не двигая часы; `scheduleAfter` считает задержку от текущего виртуального времени. `pollNext` извлекает один элемент и переводит часы на его deadline. Доставка — задача будущего driver.
10. Равное время означает FIFO по общему счётчику, включая добавление после предыдущего `pollNext`. Прошлое, отрицательная задержка, null и переполнение отвергаются до изменения очереди/часов/счётчика. Generic payload обязан быть неизменяемым; scheduler не копирует произвольные объекты.

## Альтернативы и последствия

- Синхронный I/O внутри `step` привязал бы тесты к диску/сети. Выбраны описания эффектов и внешние адаптеры.
- Реальные scheduled executors полезны будущему production runtime, но не задают воспроизводимого порядка симуляции. Для M0 достаточно JDK `PriorityQueue` и виртуальных часов.
- Граф зависимостей всех эффектов пока избыточен. Принят последовательный completion-протокол; реализация и проверки persist safety появятся вместе с storage/алгоритмом.
- Нет новых библиотек. Единственная производственная межмодульная зависимость: simulator → core (`api`, так как NodeId и clock входят в публичный интерфейс simulator).
- Контракты будут дополняться в M1–M6. WAL batch/append/truncate, replication, client proposal, apply и snapshot здесь намеренно не определены заранее.

## Свидетельства и ограничения

JUnit проверяет валидацию DTO, различие ID разных запусков, временной порядок, FIFO, воспроизводимость одинаковых входов и ошибки scheduler. Это **не** тест выборов, persist-before-response, restart или дисковой устойчивости. Данные о прогонах — в [матрице приёмки](../ACCEPTANCE.md).
