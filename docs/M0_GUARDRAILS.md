# Завершение M0: решения, архитектурные проверки и WSL

## Что закрепляет ADR-001

ADR — Architecture Decision Record, запись архитектурного решения: контекст, выбор, причина и последствия. [ADR-001](adr/0001-scope-consistency-and-failure-model.md) собирает существующие требования к v1: три постоянных узла, quorum=2, линейризуемый KV, начальный GET через журнал, модель network/crash/disk faults и границы гарантий. Наличие решения не означает, что эти свойства уже реализованы.

Например, при изоляции лидера от остальных двух узлов он не должен подтверждать новые записи только по собственной памяти. Это целевое правило majority. Его реализация и проверка появятся с Raft; M0 фиксирует договор, чтобы не менять смысл проекта по ходу разработки.

## Два разных архитектурных барьера

**Gradle `verifyCoreClasspath`** проверяет `compileClasspath` и `runtimeClasspath` модуля core. Classpath — набор внешних классов/JAR, доступных при компиляции или запуске. У production core он должен быть пустым: JDK предоставляется Java toolchain отдельно. Это запрещает даже неиспользуемые внешние зависимости, включая другие модули проекта. Зависимости тестов разрешены.

Пример нарушения:

```kotlin
// В quorum-core/build.gradle.kts такая production-зависимость сломает проверку:
"compileOnly"("org.junit.jupiter:junit-jupiter-api:5.14.4")
```

До нового барьера эта неиспользуемая зависимость не мешала тестам пройти. Теперь `test` зависит от `verifyCoreClasspath`, и сборка объясняет, что библиотеку следует перенести в адаптер или testImplementation. Отдельно проверен вариант `runtimeOnly`.

**ArchUnit 1.5.1** анализирует скомпилированные class-файлы: на какие типы ссылается код, какие методы вызывает и какие поля использует. Подключён только `com.tngtech.archunit:archunit` через testImplementation; правила запускает уже существующий JUnit 5. Отдельный test engine не нужен. Производственный core не получает ArchUnit или его транзитивную SLF4J API.

Четыре правила проверяют:

1. Все production-классы core находятся внутри его собственного пакета.
2. Используемые типы принадлежат этому пакету или `java..`; сторонние библиотеки/фреймворки запрещены.
3. Нет прямых зависимостей от I/O, сети, SQL, logging, потоков/executors, process/runtime, системных часов и конкретных генераторов случайности. Полный список задан в CoreArchitectureRules. `java.nio` запрещён целиком: бинарные codecs/ByteBuffer пока относятся к storage/transport, а не к протоколу.
4. Нет скрытого доступа через System/Math.random/UUID.randomUUID/`java.time.*.now` и parallel streams. Анализируются вызовы **и ссылки на методы**; System.arraycopy разрешён как операция над переданными массивами.

```java
LongSupplier clock = System::nanoTime; // Будет найдено как method reference.
long time = injectedClock.nowNanos();  // Работа через явно переданный порт допустима.
```

System properties/environment и консоль тоже не должны быть источниками поведения core. `Duration.ofMillis(5)` разрешён: это вычисление значения, а не чтение текущего времени. Даже seeded `new Random(42)` внутри core запрещён: источник случайности должен оставаться явной зависимостью через RandomSource.

`CoreArchitectureTest` получает от Gradle пути **всех production class directories**, а не только ищет ожидаемый Java package. Поэтому новый класс в неправильном пакете тоже проверяется. Пустой импорт приводит к ошибке. Test fixtures не входят в проверяемый production-набор. Для этой suite нужен запуск через Gradle; запуск отдельного теста кнопкой JUnit в редакторе без Gradle property сообщает об отсутствующей конфигурации.

`CoreArchitectureRulesTest` содержит 11 намеренно запрещённых примеров и один допустимый. Эти классы только компилируются/анализируются — их I/O/Thread/Random методы не выполняются. Дополнительно временный `probe.ForbiddenClockProbe` в main с `System::nanoTime` сделал обычный корневой `test` красным; probe удалён перед итоговой сборкой.

Это статическая защита от типичных прямых нарушений, а не sandbox против reflection/native обходов, не доказательство всего детерминизма и не проверка алгоритма Raft.

## Linux-стенд

WSL2 запускает Linux-среду на Windows. Проверенная конфигурация: Ubuntu 26.04.1 LTS, kernel `6.18.33.2-microsoft-standard-WSL2`, OpenJDK 21.0.12.1; `findmnt` показал ext4 (`/dev/sdd`, `data=ordered`). Это наблюдение конкретного стенда, не обязательные версии для всех машин.

Основные исходники остаются в Windows checkout и VS Code. [scripts/test-wsl.sh](../scripts/test-wsl.sh) — Bash-скрипт для создания свежего снимка и запуска сборки в Linux. Bash исполняет команды; rsync копирует перечисленные Git файлы; findmnt проверяет реальную файловую систему пути.

Запуск из PowerShell:

```powershell
wsl.exe -d Ubuntu --cd /mnt/c/Daniyar/MyProjects/MyOwn/QuorumLab --exec bash scripts/test-wsl.sh
```

По умолчанию используется `$HOME/quorumlab-lab` внутри WSL, на этой машине `/home/amateru/quorumlab-lab`. Необязательный аргумент — другой каталог стенда на ext4 вне рабочего checkout.

```text
quorumlab-lab/
  data/                  # место для будущих данных узлов M1; WAL ещё нет
  runs/run-<unique>/
    source/              # снимок для этого прогона, без .git
    files.list0          # список скопированных файлов с разделителем NUL
    source.sha256        # хэши исходных файлов до сборки
    environment.txt      # source HEAD, dirty status, Java/kernel/filesystem
    build.log
```

Каждый запуск создаёт новый каталог через mktemp. Копируются текущие tracked-файлы и новые неигнорируемые файлы, включая незакоммиченные изменения. Удалённые файлы пропускаются; `.git`, игнорируемые build/cache/tmp и `.env` не копируются. Скрипт не удаляет старые прогоны, не перезаписывает node data и не создаёт вторую Git-ветку/worktree. Для редактирования используется исходный Windows checkout.

Почему не `/mnt/c`: этот путь показывает Windows-диск через WSL (`9p` на проверенной машине). Скрипт отвергает его до запуска сборки. Ext4 — Linux-файловая система внутри WSL; каталог исходников и будущий data-dir проверены через findmnt. Сам факт ext4 не доказывает fsync, recovery или устойчивость к отключению питания.

Сборка выполняется с `clean test build --no-build-cache`. Во время первого прогона Gradle переиспользовал часть прежних результатов тестов. Для отдельного filesystem-стенда это нежелательно, поэтому build cache отключён и Linux-прогон повторён: тесты должны выполняться здесь, что особенно важно для M1. Кэш скачанных зависимостей Gradle сохраняется — повторно скачивать библиотеки не требуется.

Manifest позволяет проверить, какие именно исходники участвовали в прогоне, даже если source HEAD ещё старый и есть незакоммиченные изменения. Новая документация после прогона не выдаётся за часть старого снимка; при изменении исполняемого кода нужна новая проверка.

## Gate и следующий этап

Новые правила включены в обычный `test`, поэтому существующий GitHub workflow автоматически запускает их в обоих jobs. Изменять workflow не потребовалось. Локальные свидетельства и количество тестов — в [ACCEPTANCE](ACCEPTANCE.md). Окончательный M0 gate ждёт фактического CI этого среза после пользовательского push.

Далее M1: формат WAL, CRC32C, hard-state persistence и replay/crash recovery на выбранном стенде. Пока нет WAL, эта работа подтверждает готовность окружения, а не дисковые гарантии.
